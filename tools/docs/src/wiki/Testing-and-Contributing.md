# Testing and Contributing

## Running the tests

```
cargo test                                      # everything below except the slow and fuzz parts
cargo test --release --test stress -- --ignored # 10 MB wall-clock runs
cargo bench                                     # throughput and scaling (criterion)
```

## What is tested

- **Unit tests per stage:**
  - `tests/parser.rs`: syntax trees and rendered syntax errors (insta snapshots in `tests/snapshots/`);
  - `tests/check.rs`: one test per diagnostic code;
  - `tests/compile.rs`: IR snapshots;
  - `tests/earley.rs`: recognition;
  - `tests/disambiguate.rs`: each preference rule and when ambiguity is (not) reported;
  - `tests/eval.rs`: values and templates;
  - `tests/cli.rs`: the binary;
  - `tests/lsp.rs`: the language server, driven through an in-memory connection like an editor would;
  - `tests/editors.rs`: the editor files stay in step with the language (the Sublime syntax knows every keyword and function).
- **Golden cases:** `tests/cases/<name>/` holds `query.tql` and `input.txt` with `expected.json`, `.err` or `.warnings`
  (`tests/golden.rs`). Regenerate with `UPDATE_GOLDEN=1 cargo test --test golden` and review the diff. The cases include invoices, CSV, HTTP headers,
  a web server access log, a game playtest log, and the `aoc2025_*` cases, which structure the example inputs of all 12
  [Advent of Code 2025](https://adventofcode.com/2025) puzzles; the puzzle text is Eric Wastl's, so keep them out of public repositories.
- **Property tests** (`tests/properties.rs`):
  - the Earley parser agrees with an independent naive matcher on random grammars and inputs;
  - text generated from a random grammar always matches;
  - printing and re-parsing a random syntax tree is the identity;
  - arbitrary queries and inputs never panic;
  - the input model (word and number runs, positions) agrees with the reference's own segmentation.
- **Stress tests** (`tests/stress.rs`) assert linear scaling on deterministic step counts, bounded behaviour on pathological grammars, and 20,000-deep nesting on a
  2 MiB test thread. The 10 MB wall-clock tests are `#[ignore]`d and run with the `--release ... --ignored` command above.
- **Doc test:** the example in `src/lib.rs` runs with `cargo test --doc`.

## Fuzzing

`fuzz/` is a separate package (not part of the main workspace) with the targets `fuzz_parse`, `fuzz_input` and `fuzz_run` and a dictionary:

```
cargo +nightly fuzz run fuzz_parse -- -dict=fuzz/txtql.dict     # needs cargo-fuzz and a nightly toolchain
cd fuzz && cargo run --release --bin smoke -- SECONDS           # the same checks on random data, without nightly
```

## Benchmarks

`benches/scaling.rs` measures throughput on generated rhymes and log lines at 100 KB, 400 KB and 1.6 MB, with and without the ambiguity check, and on nested
repetitions, so linear scaling can be seen by comparing sizes. See [[Performance and Limits|Performance-and-Limits]].

## The specification

The behaviour of txtql is specified in Allium: `txtql.allium` (the system) and `spec/` (`language`, `compilation`, `running`,
`diagnostics`, `editor`). It was distilled from the code and its tests. When behaviour changes, change the code, the tests and the spec together.

## Conventions

- Code is formatted with `rustfmt` (`rustfmt.toml`: 120 columns).
- Every diagnostic has a stable `txtql::...` code, and every code has a test (`tests/check.rs`) and, where it applies, a golden case.
- Add a golden case under `tests/cases/` for a new language feature or diagnostic, and review the diff when regenerating.
- This wiki's examples were generated by running the binary; when behaviour changes, re-run the examples before editing the text.
